# HeritageMind v1.8：动态 Agent 协作与实时工作流可视化设计

**状态：** 已确认，待实施  
**范围：** 仅实现 v1.8 主链——动态协作与实时执行可视化。Agent 评估、用户反馈、Agent 管理后台不在本期。

## 1. 目标与边界

v1.8 让一次问答过程既可协作、又可被用户实时理解：Router 选出参与专家后，专家先形成初答，再按运行时参与者集合进行补充、质疑与回应，最后融合为最终答案。Vue 在生成回答期间实时呈现实际 DAG 和协作消息。

本期不改变现有知识库、检索、会话记忆、图谱查询或最终答案生成的事实来源。协作轮复用首次检索得到的上下文，禁止每轮重新检索；这既控制延迟和成本，也避免把同一问题放大成多次不必要的 LLM 调用。

本期第一批注册 Agent 仍为 `craft_expert`、`history_expert`、`heritage_expert`。所谓“动态”是指 Router 和协作引擎不再写死三者的处理顺序或人数；未来新 Agent 只需注册能力与工厂即可参加运行。管理端 Agent CRUD 不属于本期。

## 2. 方案选择

采用扩展既有 `POST /query/stream` 的 SSE 协议，而不新增 WebSocket 或状态轮询。

- SSE 已是前端流式问答的传输通道，最小化认证、连接管理与兼容风险。
- 旧事件的 `step` 与 `msg` 字段继续存在；新增 `event` 字段使 v1.8 客户端能识别结构化生命周期事件。
- 浏览器刷新后不恢复已结束的实时动画；聊天历史继续显示既有最终回答和静态轨迹，不伪造实时过程。

## 3. 后端架构

### 3.1 Agent 注册表

新增一个只读注册表，唯一负责：

1. 将 Agent ID 映射为展示元数据（名称、能力标签、图标）与实例工厂；
2. 校验 Router 返回的 Agent ID，只保留注册的、去重后的参与者；
3. 为协作引擎提供本次参与者集合，而非固定专家优先级。

Dispatcher 的函数调用 schema 从固定的三项枚举中生成允许的注册 Agent ID。现有关键词降级也只能返回已注册 Agent。未知 Agent 绝不实例化，也不出现在 SSE 事件中。

### 3.2 协作引擎

现有专家分派保留其“首轮检索并初答”的责任。新的协作阶段接收：用户问题、已验证的参与者、首轮回答和共享上下文，并生成一个有上限的协作计划。

每条协作消息包含：

```json
{
  "from_agent": "history_expert",
  "to_agent": "craft_expert",
  "kind": "challenge",
  "summary": "请补充该工艺变化与所处历史阶段的对应依据。"
}
```

`kind` 仅允许 `supplement`、`challenge`、`response`、`agree`。`summary` 为面向用户的短摘要，不传递系统提示词、完整内部推理、完整检索文本或密钥。

计划最多执行配置化的有限轮次；参与者少于两名、协作计划无有效动作、或任一协作调用失败时，跳过或降级到当前融合逻辑。单个专家首答失败时记录 `fallback`，其余专家、协作及融合照常进行。最终答案仍由已有融合/生成节点生成。

### 3.3 实时运行事件

工作流使用事件发射器在节点边界和协作消息产生时写入运行事件。`/query/stream` 在保留旧的进度事件基础上发送：

| `event` | 关键字段 | 时机 |
|---|---|---|
| `workflow_started` | `run_id`, `nodes`, `edges` | 开始执行，携带基础 DAG |
| `node_started` | `node_id`, `message` | 节点开始 |
| `node_completed` | `node_id`, `message`, `elapsed_ms` | 节点成功完成 |
| `node_skipped` | `node_id`, `message` | 条件分支跳过 |
| `node_fallback` | `node_id`, `message`, `elapsed_ms` | 安全降级但链路继续 |
| `workflow_graph_updated` | `nodes`, `edges` | Router 确认实际参与 Agent 后添加动态节点和边 |
| `agent_message` | `from_agent`, `to_agent`, `kind`, `summary` | 协作消息可展示时 |
| `done` | 已有答案字段、`workflow_trace`、`collaboration_messages` | 全部完成 |
| `error` | `msg` | 无法恢复的流式错误 |

每个结构化事件都同时保留 `step` 和 `msg`。执行轨迹仍写入最终普通 `/query` 响应，确保非流式接口和历史功能兼容。`run_id` 只在一次 SSE 连接内使用，不写入会话表。

## 4. 工作流 DAG

基础路径为：

```text
analyze_question → plan_question? → dispatch_to_experts
                                      ├─ agent:<id> (0..N)
                                      └─ query_graph
                  → collaborate? → fuse_knowledge → detect_gaps → generate_response
```

其中 `plan_question`、`collaborate` 与 `query_graph` 可以按现有路由/条件被跳过；被跳过节点必须发送 `node_skipped`。动态 Agent 节点只在 Router 结果已验证后通过 `workflow_graph_updated` 出现。协作消息在 DAG 上表现为 Agent 节点之间的有向虚线，时间线同时按发生顺序呈现。

## 5. 前端交互

新增实时工作流组件，挂载在当前流式回答对应消息下方：

- 接收 `workflow_started` 后创建运行时状态和基础 DAG；
- 接收节点事件后立刻更新节点状态：`pending`、`running`、`completed`、`skipped`、`fallback`；
- 接收 `workflow_graph_updated` 后合并动态节点与边，不重复渲染；
- 接收 `agent_message` 后将协作边标记为已发生，并在时间线追加一条脱敏摘要；
- 流式进行时默认展开；`done` 后保持最终状态并允许折叠；
- 对没有 v1.8 实时事件的历史消息，继续使用 v1.6 的静态 `WorkflowTrace`，不显示实时 DAG。

组件使用项目现有 Vue、Tailwind/CSS 和 SVG 连线，不引入图编辑器依赖。颜色与文案沿用现有宣纸底、朱砂强调的设计：执行中为朱砂强调，完成为低饱和绿，跳过为中性灰，降级为琥珀色。

## 6. 兼容性与失败处理

- `/query` 的响应模型和既有字段不移除；新增字段只给 v1.8 消费者使用。
- SSE 客户端若仅认识旧 `step/msg`，仍能显示旧的进度消息。
- 连接中断会触发已有 `finally` 清理请求级模型覆盖；不记录“已完成”的错误状态。
- 动态 Agent ID、事件状态、消息类型均在后端白名单校验；不信任 LLM 直接产生的 UI 标识。
- Agent/协作异常在事件中显式标为 `fallback`，不得以虚假的 `completed` 掩盖失败。

## 7. 测试与验收

按测试先行实施。每项生产逻辑前，先写且观察到对应测试因功能缺失而失败。

后端测试：

1. 注册表过滤未知 Agent、保留 Router 选中顺序并支持任意数量的已注册 Agent；
2. 协作计划在单 Agent 时跳过，在多 Agent 时生成受轮次上限约束的合法消息；
3. 单 Agent 或协作步骤失败时发出 `node_fallback`，其余链路仍能融合回答；
4. SSE 的事件顺序、动态 DAG 更新、旧 `step/msg` 兼容以及 `done` 中的最终轨迹；
5. 所有外发事件都不含 API Key、系统提示词或完整检索上下文。

前端验证：

1. 抽出的事件归约函数将事件正确映射为节点和协作时间线状态；
2. `vue-tsc --noEmit` 通过；
3. Vite 生产构建通过。

发布验收：使用一个两专家以上的问题演示“路由 → 动态 Agent 节点 → 至少一条协作消息 → 融合”的实时展示；使用一个单专家问题演示协作节点被明确标记为跳过；模拟一个 Agent 故障演示降级而非中断。
