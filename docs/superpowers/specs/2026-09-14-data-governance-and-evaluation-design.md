# HeritageMind 数据治理、知识扩充与效果评测设计

**日期：** 2026-09-14
**状态：** 用户已确认方向，待审阅规格后进入实施计划

## 1. 目标与范围

本阶段先解决知识库规模、可信来源和效果证据三个基础问题，为后续工程化收口与前端重设计提供可靠数据底座。

当前 `data/crafts/` 有 23 个以技艺名命名的文本文件。检索脚本的 Hit@5 只验证目标技艺是否进入前五个结果，且部分问题因锚词不存在而被排除；它不能代表答案事实正确率。现有回答过程评分也只评价引用、执行轨迹和知识缺口披露，不能代表事实正确率。

本阶段交付：

- 可追溯、可审核、可重复导入的知识文档模型与导入流程；
- 现有 23 项资料的来源核验和迁移；
- 首批重点技艺的多来源扩充；
- 独立、版本化的检索和回答评测集，以及可复现的基线报告；
- 对现有 CI 的评测冒烟和数据校验补充。

本阶段不自动爬取网站、不将模型生成文字作为权威资料、不把未核验的外部资料发布到公开知识库，也不在本期重做 Vue 页面。前端将先消费新增的来源、证据定位和质量状态字段，视觉重设计另立规格实施。

## 2. 数据来源与审核原则

资料以公开、可核验的第一方或权威机构材料为优先级：文化和旅游主管部门、中国非物质文化遗产网、博物馆、图书馆、大学/研究机构及项目保护单位。每份资料必须登记标题、发布机构、原始链接、访问日期、许可证或使用说明（已知时）与可定位的证据片段。

采集动作不由运行时服务自动完成。资料先以本地导入包进入 `data/knowledge_sources/`，经过结构和来源校验后，以 `draft` 状态进入数据库；管理员审核后变为 `published`，才参与生产检索。来源失效、事实争议或版权状态不清楚时标为 `deprecated` 或保留为 `draft`，不会作为公开回答证据。

首批扩充采用“深度优先”：景泰蓝、苏绣、龙泉青瓷、南京云锦、京剧、皮影戏六种技艺各补入至少两份独立来源。已有 23 个旧文本不因暂未找到来源而删除，但在迁移后标记为 `legacy_unverified`，只在开发环境可选参与检索；正式数据集和公开检索默认只使用已发布资料。

## 3. 数据模型与文件组织

新增或扩展模型采用 SQLAlchemy 和 Alembic：

- `knowledge_documents`：文档 ID、技艺 ID、标题、正文、文档类型、语言、来源状态、导入时间、内容哈希与发布状态；
- `knowledge_sources`：机构、原始 URL、访问日期、许可证/版权说明与可选永久链接；
- `knowledge_evidence`：文档段落或字符范围、对应来源、摘录和事实标签；
- `knowledge_ingest_runs`：导入批次、输入清单、统计、失败原因和数据集版本。

文档和来源是一对多关系；证据绑定到一个文档片段和一个来源。向量库的 metadata 至少包含 `document_id`、`craft_id`、`evidence_id`、`dataset_version` 和 `publication_status`。回答引用应返回技艺名、文档标题、来源机构、URL 和对应片段，而非只返回模糊的“知识库”。

导入包使用 JSON 或 YAML 清单加 UTF-8 正文文件。清单定义稳定 ID、来源字段、技艺关联和审核状态；正文内容与元数据分离。导入服务以内容哈希去重，同一来源更新时创建新版本并保留旧版本审计信息。现有 `data/crafts/*.txt` 通过一次性迁移器转入这一格式，保证原文件不被原地改写。

```text
data/
  knowledge_sources/
    manifest.json             # 文档、来源、状态和版本
    documents/                # 导入的 UTF-8 正文
  crafts/                     # 保留为兼容输入，逐步迁移
  evaluation/
    retrieval-v1.jsonl        # 独立检索评测集
    answer-v1.jsonl           # 人工标注的回答评测集
    reports/                  # 不提交模型私钥和原始敏感日志
```

## 4. 导入、检索与引用流程

```text
本地导入包 → 清单/来源校验 → draft 文档与证据 → 管理员审核
                                              ↓
                                         published 文档
                                              ↓
切分与向量化（带 document/evidence/version metadata） → BM25 / 向量 / RRF / 重排
                                              ↓
                                  回答 + 可定位引用 + 数据集版本
```

校验失败时整份输入保持不发布，并在导入批次记录错误。向量化失败时不切换为不带来源的结果；已发布的上一版本继续可用。查询无证据或证据状态非发布时，系统明确披露知识缺口。旧的 `craft_id` 仍是聚合维度，但不再是唯一文档身份，避免同一技艺只能存一篇资料的限制。

## 5. 评测设计

评测集和知识语料必须分离：评测题、参考证据 ID、问题类型和标注人写入版本化 JSONL；题目不能从同一段原文直接改写后当作独立测试。所有基线报告记录 Git 提交、数据集版本、检索配置、模型名称、运行日期和硬件/服务模式。

### 5.1 检索评测

首个 `retrieval-v1` 至少 120 题，分为：

- 40 条实体直问；
- 30 条近似技艺或跨门类混淆题；
- 25 条跨文档比较/流程题；
- 15 条多轮指代追问；
- 10 条知识库外问题。

每题标注一个或多个可接受 `evidence_id`，不再只标注整项技艺名称。报告分别给出 Recall@1、Recall@3、Recall@5、MRR 和无答案题的正确拒答率，并按题型拆分。比较 BM25、向量、RRF 与 RRF+重排；只有在相同语料、相同题集和相同配置下，才比较结果。

### 5.2 回答评测

从检索评测中固定抽取至少 40 题，采用双人盲标或“人工标注 + 第二轮复核”。评分维度为事实与证据一致性、覆盖度、引用可追溯性、知识缺口处理和可读性，每项 0–2 分。报告展示平均分、各维度分布、分歧样本和典型失败案例；过程质量评分可保留，但必须明确标为辅助信号，不能替代人工事实评估。

多 Agent 的比较只使用复杂题子集：单路 RAG 与当前 Agent 编排执行同一输入，记录人工回答质量、端到端延迟、Token 消耗和失败率。若质量提升不足以抵消成本和延迟，应在报告中如实保留结论。

## 6. 工程化与测试

先为每个新边界编写离线确定性测试：清单字段校验、来源 URL/状态校验、哈希去重、版本更新、发布状态过滤、引用定位、旧数据迁移和导入失败回滚。评测计算函数也应有固定输入输出测试，防止“改统计脚本让分数更高”。

CI 在现有 ruff 与 pytest 之外增加：数据清单校验、轻量评测冒烟（使用小型 fixture，不加载 BGE 或调用 LLM）和 Vue 类型检查/生产构建。完整 BGE 基线保留为本地可运行命令，不塞进 GitHub Actions；生成报告写入带日期的结果文件，不能覆盖历史基线。

验收条件：

- 发布资料的来源字段完整，引用可定位到来源与证据片段；
- 同一导入包重复执行不产生重复文档或向量；
- 未发布/废弃资料不会出现在默认公开检索；
- 旧 23 项资料迁移不丢失内容，状态可被明确区分；
- `retrieval-v1`、回答评测和基线报告可由仓库命令复现；
- CI 能在不联网、不加载本地模型的环境通过。

## 7. 实施顺序

1. 定义清单格式、模型、迁移、导入校验与单元测试；
2. 迁移现有 23 项旧资料，输出缺失来源清单；
3. 创建首批六项重点技艺的来源包，审核、发布并重建索引；
4. 建立独立评测集、统计脚本和第一次真实基线报告；
5. 将数据校验、评测冒烟和前端构建接入 CI，并更新 README 的数据边界与可复现命令；
6. 以此结果为输入，单独设计前端“搜索—证据—追问”主流程。

## 8. 风险与边界

权威来源的整理速度可能限制首批资料量，因此“六项各两来源”是最低可发布门槛，不以凑数量替代来源质量。第三方材料仅在版权、机构和证据均可说明时采用。数据集的盲标工作需要明确记录标注人和复核规则；若当前只有一名标注人，报告必须写明这一局限。

不将来源页面全文或未获许可的图片批量复制进仓库。运行前获取或更新外部资料时，先检查网站使用条款、robots 约束和公开许可；存储可验证的链接、必要摘录和自行整理的事实结构，而非绕过访问限制。
