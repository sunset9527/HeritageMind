# 当多个AI专家产生分歧时怎么办？非遗多智能体系统的辩论机制设计

> 我在做一个非遗知识问答系统时发现：同一个问题，不同角度的"专家"会给出不同甚至矛盾的答案。这让我意识到多Agent系统的核心挑战不是"如何让Agent协作"，而是"如何让Agent在分歧时达成共识"。本文记录了我的多Agent架构设计、知识缺口检测和辩论机制的完整实践。

## 一、选题：为什么是非遗？

非遗（非物质文化遗产）是一个很特殊的知识领域。它不是"百度百科式"的静态知识，而是"活"的——存在传承人口中、手工技艺中、地方习俗中。

举个例子，"景泰蓝的制作流程"在百度百科上可能是500字的概述，但在工艺美术大师那里可能是5万字的经验，而且不同流派的传承人说法还不一样。**这种"知识本身就不唯一"的特性，恰好是多Agent系统的天然适用场景。**

另一方面，非遗知识面临一个紧迫问题：**传承人老龄化，很多技艺随着老匠人离世而消失。** 我想尝试用AI技术做一点微小的工作——至少把现有的知识结构化地保存下来，并能以智能的方式呈现给不同需求的人。

## 二、系统架构：三个专家 + 一个调度员 + 一位质检员

我的多Agent架构采用了"领域专家 + 中央调度"的模式：

```
用户提问
  │
  ▼
调度Agent ←── 意图分析，决定激活哪些专家
  │
  ├──→ 技艺知识Agent（工艺、材料、工具）
  ├──→ 历史文化Agent（起源、演变、文化意义）  
  └──→ 传承现状Agent（传承人、濒危程度、保护）
  │
  ▼
知识融合 ←── 多视角整合，去重补缺
  │
  ▼
知识缺口检测 ←── "我们能回答多少？有什么不知道的？"
  │
  ▼
生成回答 ←── 根据用户画像调整深度
```

关键设计决策：

**1. Agent之间不直接通信。** 每个Agent只和调度Agent交互，避免N对N的通信复杂度爆炸。调度Agent负责分解问题、分发子任务、融合结果。

**2. Agent有明确的知识边界。** 技艺Agent不会去回答历史问题，历史Agent不会去讲工艺流程。这不是技术限制，是设计选择——有边界才能保证回答的可靠性。

**3. 知识缺口检测是独立环节。** 不是Agent自己说"我不知道"，而是一个独立的GapDetector来分析整个知识库的覆盖情况。

## 三、深度点1：知识缺口——能回答"不知道什么"

这是我个人最满意的设计。大多数问答系统有一个隐含假设：**知识库是完备的，所有问题都能回答。** 但现实中，知识库永远不可能是完备的。

我的GapDetector的设计逻辑：

```python
class GapDetector:
    def detect_gaps(self, query, retrieved_docs, agent_outputs):
        # 1. 提取问题中的所有实体和关系
        entities = self._extract_entities(query)
        
        # 2. 检查每个实体在知识库中的覆盖程度
        coverage = {}
        for entity in entities:
            docs_mentioning = self._count_docs(entity, retrieved_docs)
            detail_level = self._assess_detail_level(entity, retrieved_docs)
            coverage[entity] = {
                "found": docs_mentioning > 0,
                "detail": detail_level,  # 'none' | 'shallow' | 'moderate' | 'deep'
            }
        
        # 3. 生成缺口报告
        gaps = []
        for entity, cov in coverage.items():
            if cov["detail"] in ("none", "shallow"):
                gaps.append({
                    "entity": entity,
                    "current_coverage": cov["detail"],
                    "suggestion": f"建议补充 {entity} 的详细资料"
                })
        
        return gaps
```

当用户问"芜湖铁画和龙泉宝剑的锻打工艺有什么区别"时，系统可能对芜湖铁画有详细知识，但对龙泉宝剑只有简介。这时GapDetector会在回答后附加：

> 知识覆盖提示：当前知识库对"芜湖铁画"的覆盖程度为85%（详细），对"龙泉宝剑锻打工艺"的覆盖程度为30%（仅有概述）。以下回答中关于龙泉宝剑的部分可能不够深入，建议补充相关资料。

**承认"我不知道"比假装全知更有价值**——这是这个系统的核心设计哲学。

## 四、深度点2：辩论引擎——当专家意见不一时

### 4.1 真实的分歧场景

在测试中我发现了一个有趣的问题：用户问"苏绣最核心的技艺特点是什么"，技艺Agent强调"劈丝技术"，历史Agent则强调"仿画绣的写实风格"。两个答案都对，但角度完全不同，直接拼接会显得矛盾。

### 4.2 辩论机制设计

我实现了一个DebateEngine来处理这种情况：

```
1. 检测分歧
   - 当两个Agent的置信度都>0.7但核心观点不同时触发
   
2. 辩论回合（最多3轮）
   第1轮：
     技艺Agent: "苏绣的核心是劈丝——一根丝线劈成64份，这是其他刺绣做不到的"
     历史Agent: "苏绣因沈寿引入西洋画法而闻名，核心是写实性突破"
     
   第2轮（互相评议）：
     技艺Agent回应: "劈丝是苏绣区别于其他绣种的独门技艺，写实性是风格层面"
     历史Agent回应: "没有写实性突破，劈丝只是技术细节，不会让苏绣成为四大名绣之首"
     
   第3轮（综合）：
     调度Agent: "两位的观点并不矛盾——劈丝是技术层面的核心，写实性是艺术层面的突破。
                 建议在回答中将两者作为不同维度呈现。"
                 
3. 辩论过程可视化
   用户在界面上可以看到完整的辩论时间线，每条论点标注来源Agent
```

**这里有个重要设计：辩论不是为了"辩出谁对谁错"，而是"找到不同观点的成立条件。"** 很多时候Agent之间的分歧不是真伪问题，是视角问题。

### 4.3 踩坑：辩论无限循环

早期版本有一个bug：两个Agent在互相评议时进入了"你说A→我说B→你再说A→我再说B"的无限循环。问题出在评议Prompt中没有"收敛"的约束。

修复方案：在每轮辩论的Prompt中加入——

```
如果你发现本轮观点与前一轮观点本质相同，只是表述不同，请回复"CONVERGE: [共同点]"而不是继续反驳。
```

加入这个指令后，辩论平均收敛在2.3轮，不再出现无限循环。

## 五、深度点3：多粒度输出——同一答案给不同的人看

非遗知识的一个特点是：不同人对"好的回答"的定义完全不同。

- 一个游客问"景泰蓝是什么"：需要300字的趣味介绍
- 一个设计系学生问同样的问题：需要800字带工艺流程说明
- 一个非遗研究者问同样的问题：需要2000字带材料学分析和文献引用

我通过**用户画像 + Prompt模板 + 参数控制**三级机制实现：

```python
# 用户画像配置
PROFILES = {
    "curious": {  # 好奇者
        "max_tokens": 500,
        "temperature": 0.8,  # 更有趣但不一定严谨
        "template": "用通俗易懂的语言介绍{craft}，可以加入有趣的故事和比喻"
    },
    "learner": {  # 学习者
        "max_tokens": 1500,
        "temperature": 0.4,
        "template": "系统性地介绍{craft}，包括：历史渊源、工艺流程、艺术特点、代表作品"
    },
    "researcher": {  # 研究者
        "max_tokens": 5000,
        "temperature": 0.1,  # 严谨优先
        "template": "深入分析{craft}，包括：材料学分析、几何结构研究的差异、传承谱系..."
    }
}
```

**效果验证：** 用同一问题"宜兴紫砂壶为什么适合泡茶"，三个画像得到的回答长度分别是423字、1240字、2300字——不仅长度不同，信息密度和学术深度也完全不同。

## 六、反思

### 做得好的
- 知识缺口检测确实解决了"AI不懂装懂"的问题
- 多粒度输出模型在测试中获得了用户的积极反馈
- 辩论机制让多Agent的交互变得透明可解释

### 需要改进的
- 目前只有3个专家Agent，领域覆盖有限。扩展更多专家时，调度器的复杂度会O(n²)增长
- 辩论机制依赖LLM的文本推理能力，在高度专业化的技术分歧上可能不够可靠
- 知识图谱目前是手工构建的，扩展到更多非遗项目需要自动化构建方案

### 对多Agent开发者的建议
1. **先定义好Agent的知识边界，再设计协作机制。** 边界模糊的Agent一定比边界清晰的更难管理
2. **分歧处理不是"选一个对的"，是"整合多个对的"。** 真正的价值在于多视角，而不是找出唯一正确答案
3. **承认不知道是美德。** 加一个知识缺口检测的成本很低，但用户信任度的收益很高
